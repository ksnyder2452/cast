Performance and Security recommendations and considerations

 

 

Notes

(To some extent) both security and performance can be addressed by how you configure your environment. Different recommendations and requirements are included here to help you pick the best configuration

 

 

Basic Concepts

·         Each CAST Service is an independent .Net Application. They all use RabbitMQ as the Communication Channel

·         All information is stored in the central (MySQL) database. That includes both CAST-specific information (such as Service State) and Client information (such as Status)

·         Each Service can run on an isolated environment (such as a Hosted VM) – they do not need to exist on a single environment. All Services need RabbitMQ connectivity, but some do not need a direct database connection

·         The Health Service will run some scheduled cleanup tasks (if it is running on the same hosted environment as your RabbitMQ instance). Otherwise, those cleanup steps will fail - but the Health Service will continue running as normal

·         The recommended RabbitMQ and MySQL configurations (in the README.md file) try to adhere to Least Privilege

·         Every Service and Client has a properties file that must be configured for your environment

 

 

Services

·         Logger Service. Primary purpose is to support communications (messages) between the backend database and Services

o    Requires both RabbitMQ and MySQL Connections

o    RabbitMQ

§  Maintains a Queue called logger\_service. This Queue will be very active (since no other Service will submit ExecuteUpdate statements against the database)

o    MySQL

§  Only submits ExecuteUpdates against the database (no queries)

·         Execution Service. Primary purpose is to support communications (messages and files) between Services and all Clients

o    Requires a RabbitMQ Connection

o    RabbitMQ

§  Maintains a Queue called execution\_service

§  Will push messages to the logger service

§  Will push messages to each Client

§  Is the primary channel for pushing messages and files to all Clients through distinct Client Queues

·         Scheduler Service. Primary purpose is to schedule future Runs

o    Requires both RabbitMQ and MySQL Connections

o    RabbitMQ

§  Maintains a Queue called scheduler\_service

§  Will push messages to the logger service

§  When a schedule has been hit will submit a message to the execution service Queue starting the Client run

o    MySQL

§  Poll the Client state for Scheduled runs

·         File Storage Service. Primary purpose is to support moving files between itself and all Clients

o    Requires a RabbitMQ Connection

o    RabbitMQ

§  Maintains a Queue called file\_storage\_service

§  Will push messages to the logger service

§  Files are sent as binary messages (and therefore there is a max file size limitation of 10m

§  All files are Zipped prior to sending

·         Health Service. Primary purpose is to scan for Service status (and update the MySQL database when the status changes). It will also cleanup old information, as well as remove old Message Queues if they are inactive

o    Requires both RabbitMQ and MySQL Connections

§  RabbitMQ

·         Connection is strictly used to determine whether a Queue is unavailable

·         If a Queue is unavailable the MySQL database will be updated to reflect this

o    All Queues are monitored in this fashion (Services and Clients)

o    If a Client state is set to COMPLETED (and it's been over 30 minutes) the Health Service will attempt to manually delete the Queue

o    If it's been over 720 minutes (regardless of Client state) the Health Service will attempt to manually delete the Queue

·        Client Service

o    Every Client instance will maintain its own (distinct) Queue

o    Will push messages to the logger service

o    Will push and pull messages with the execution service

o    Will push and pull messages with the file storage service

 

 

 

Execution UI

o    Primary purposes are to display the state of CAST Services (and all Clients) and to submit Actions to each Client

o    Requires both RabbitMQ and MySQL Connections

o    RabbitMQ

§  Submit Action requests to the Execution Service (for each Client)

o    MySQL

§  Retrieves the state of everything to be displayed

 

 

RabbitMQ

The recommended configuration is defined in README.md. This configuration is intended to follow the rule of Least Permissions (as closely as possible)

 

 

MySQL

The recommended configuration is defined in README.md. Again, this configuration is intended to follow the rule of Least Permissions (as closely as possible)

 

 

 

 

Based on the above information these are the general security and performance considerations. Note the assumption that (in every case) you can only run 1 Client per machine. Also note the assumption that your MySQL Server instance is generally hosted separately

 

The primary decision you need to make is where you want to host the Services, RabbitMQ Server and MySQL instance. For example

o   Hosting all Services on a single VM, RabbitMQ hosted separately, MySQL hosted separately has the following benefits and constraints

o    Benefits

§  Reduced network traffic

§  Ability to lock down access to and from the VM

o    Constraints

§  Health Service will not support automatic cleanup

o    Hosting all services on the same VM as a RabbitMQ Server, MySQL hosted separately has the following benefits and constraints

o    Benefits

§  Reduced network traffic

§  Ability to lock down access to and from the VM

§  Health Service will support automatic cleanup

o    Constraints

§  Process load

o    Hosting each service on a distinct VM, RabbitMQ hosted separately, MySQL hosted separately

o    Benefits

§  Ability to lock down access to and from the VMs

§  service can support load up-to the hosted VM

o    Constraints

§  Network traffic

§  Service will not support automatic cleanup

§  Amount of setup

o    Hosting each service on a distinct VM, RabbitMQ hosted on same VM as Health Service, MySQL hosted separately

o    Benefits

§  Ability to lock down access to and from the VMs

§  service can support load up-to the hosted VM. Note that the VM hosting both RabbitMQ and the Health Service will have more load than normal

o    Constraints

§  Network traffic

§  Amount of setup

o    Hosting everything on a single Docker Container

o    Benefits

§  Reduced network traffic

§  Ability to lock down access to and from the Container

o    Constraints

§  Performance is constrained by the Container

§  Not really production-worthy

 

Limitations

The following limitations exist around Load

·         All data transfers (messages and files) are handled by the RabbitMQ Server. Therefore, the default max payload size is 16mb. This number is configurable within RabbitMQ

o    All files are compressed prior to transport

·         The max number of Queues is dependent on your RabbitMQ/ERLang configuration. By default it is around 32768

o    Each CAST Service has it’s own Queue, as well as each Client
